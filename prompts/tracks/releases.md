# Track: releases and betas

Use supplied landed release metadata, the release calendar, official preview notes, and the edition date to report release moments accurately. Monday editions are a natural place to frame a beta or the week ahead when there is useful reader-facing context.

A configured product's scheduled stable release day is the exception to the normal selectivity rule: it must produce a release article, and that article must be the edition's headline lead. Build it around a small number of consequential, source-supported themes rather than reproducing or enumerating the release notes.

On a configured stable release day, treat features in the official release source as release contents. Write confidently about what the release brings and that it arrives today. Do not expose source-draft boilerplate, describe features as provisional, mention missing stable artifacts, or append availability disclaimers. Exact `available now` or artifact claims may use landed stable-release metadata, but missing metadata must not become part of the story.

Betas, prereleases, release candidates, and patch releases remain optional. Publish one only when readers gain a separate, human-relevant outcome beyond the radar: a materially important change worth testing, a consequential fix, or a concrete connection to verified work. Never infer release contents from timing or metadata. Dependency updates and test-only additions remain maintenance even when they land near a release.
